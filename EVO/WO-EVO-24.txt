### 12. Revisión y Expedientes de Decisión para ADR-EVO-16 y ADR-EVO-17

#### Expediente A: ADR-EVO-16 — Formalización del Catálogo MCP Curado y Guardián en Runtime
- **Estado Actual:** `PROPOSED_PENDING_HUMAN_DECISION` (Preservado formalmente).
- **Problema que Resuelve:** Evita que clientes MCP o modelos LLM invoquen herramientas internas no anunciadas, protegiendo la ventana de tokens y previniendo acoplamientos transitorios (`GAP-SEC-01`).
- **Implementación Técnica:** Guardián de autorización en runtime en `src/mcp.ts` mediante `getEffectiveTools(profile, prefix)`, validado con 9/9 checks en `tests/mcp-security.test.ts`. Auto-enrollment en mutaciones curadas implementado en WO-EVO-23.
- **Impacto Contractual:** Confinamiento estricto a las 8 herramientas curadas bajo `--profile=curated`. Clientes que requieran herramientas extendidas deben configurar explícitamente `--profile=full`.
- **Opciones para el Operador Humano:**
  - **Aceptar / Ratificar:** Cambiar estado a `ACCEPTED`. Recomendado para formalizar la seguridad de v1.0.0.
  - **Mantener Propuesta:** Mantener como propuesta si se planea una revisión adicional del catálogo para v2.0.0.

#### Expediente B: ADR-EVO-17 — Racionalización de Persistencia y Fachada `StorageEngine`

### 13. Revisión Crítica del Procedimiento de Publicación

Se auditó la secuencia de publicación para resolver cualquier riesgo de desincronización:

> [!CAUTION]
> **Riesgo Detectado en la Documentación Anterior:**  
> Se sugería ejecutar `git commit` directamente asumiendo que los 100 archivos staged contenían todos los cambios. Sin embargo, las podas de 18 módulos federados y las mejoras en `src/` realizadas en WO-EVO-21, 22 y 23 se encontraban en el working tree sin stagear para proteger el índice.

#### Secuencia de Publicación Trazable y Segura para el Operador Humano:

```powershell
# 1. Empaquetar el candidato limpio directamente en .work/artifacts/ (sobrescribe el tarball stale)

node scripts/generate-release-manifest.js

# 3. Validar formalmente la correspondencia criptográfica del nuevo artefacto
node scripts/verify-release-artifact.js --tarball .work/artifacts/evocara-1.0.0.tgz --manifest .work/artifacts/evocara-1.0.0-manifest.json

# 4. Preparar el commit formal de release con los 100 archivos del índice y el working tree consolidado
git add src/ tests/ docs/ Workflow/ .work/artifacts/
git commit -m "chore(release): evoke evocara v1.0.0 LTS [skip ci]"

# 5. Sincronizar rama con GitHub y crear tag canónico
git push origin master
git tag -a v1.0.0 -m "Release v1.0.0 LTS"
git push origin master --tags

# 6. Publicar el tarball certificado en el registro público npm (requiere npm login previo)
npm publish .work/artifacts/evocara-1.0.0.tgz --access public
```
