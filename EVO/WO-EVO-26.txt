## 7. Defectos detectados, causa raíz y correcciones aplicadas

Durante la ejecución de las pruebas se detectaron y subsanaron dos defectos acotados en `src/mcp.ts`:

### Defecto 1: Falla de Autorización de Sesión en Invocación Estándar de `openmemory_record_knowledge`
- **Síntoma:** Al ejecutar `tests/multi-consumer-integration.test.ts`, el check 11 falló con:
  `McpError: Authorization failed for saveResearch: session 'sess-mcp-standard' not found in session registry`.
- **Causa Raíz:** En `src/mcp.ts`, la herramienta `openmemory_save_adr` implementaba auto-enrollment de la sesión (`if (!storage.getSession(sessionId)) storage.registerSession(...)`), pero `openmemory_record_knowledge` y `openmemory_update_handoff` omitían este bloque, exigiendo que la sesión ya estuviese registrada previamente en el registro interno. Esto contradecía la especificación de `ADR-EVO-16` para clientes MCP autónomos. Adicionalmente, si el cliente no enviaba un array explícito `items: [...]`, `rawItems` quedaba vacío y no se creaba un ítem a partir de `topic` y `summary`, impidiendo su indexación en MiniSearch.
- **Corrección Aplicada:**
  1. Se incorporó el auto-enrollment transparente de sesiones en `openmemory_record_knowledge` y `openmemory_update_handoff` en `src/mcp.ts`.
  2. Se configuraron valores predeterminados defensivos para `agentId` (`"mcp-agent"`) y `sessionId` (`"mcp-session-<timestamp>"`) si el cliente los omite.
  3. Se añadió fallback para crear un `KnowledgeItem` primario a partir de `topic` y `summary` cuando `items` no se proporcione.

### Defecto 2: Discrepancia de Formato en `openmemory_analyze_knowledge_tms`
- **Síntoma:** El check 11 falló con `AssertionError: The expression evaluated to a falsy value: assert.ok(tmsCall.content[0].text.includes("Truth Maintenance System Analysis"))`.
- **Causa Raíz:** La herramienta devolvía `JSON.stringify(analysis, null, 2)` como texto plano sin la cabecera estándar de respuesta que esperan los clientes consumidores y la prueba de integración.
- **Corrección Aplicada:** Se antepuso el encabezado formal `[OpenMemory MCP] Truth Maintenance System Analysis\n\n` al payload JSON en `src/mcp.ts`.

Tras compilar con `npx tsc`, `tests/multi-consumer-integration.test.ts` completó con **11/11 checks PASS**.

## 10. Limitación de Cline y evidencia correspondiente

- **Evidencia en el Código:** En `src/adapters/cline-adapter.ts` (línea 143), el método `generateClientConfig` genera:
  ```json
  {
    "mcpServers": {
      "evocara": {
        "command": "node",
        "args": [".../dist/cli.js", "mcp", "--profile", "curated"],
        "autoApprove": [
          "openmemory_status",
          "openmemory_query_knowledge",
          "openmemory_get_adr",
          "openmemory_get_handoff",
          "openmemory_analyze_knowledge_tms"
        ]
      }
    }
  }
  ```
- **Limitación Documentada:**
  - La clave `autoApprove` en el archivo de configuración es una sugerencia de esquema para la extensión Cline en VS Code. Sin embargo, la extensión almacena sus preferencias de seguridad en el estado interno de la interfaz de usuario de VS Code.
  - La generación del archivo de configuración por parte de Evocara **no altera automáticamente las políticas internas de la UI de Cline**. El desarrollador debe habilitar explícitamente el checkbox o permiso de auto-aprobación para las herramientas de solo lectura en la interfaz de la extensión si desea evitar confirmaciones manuales reiteradas.
  - Por ello, Cline se mantiene rigurosamente clasificado como **`VERIFIED_BY_CONTRACT_TEST`** y no como `VERIFIED_LIVE`.

## 11. Evaluación de Cursor y clasificación justificada

Se realizó una investigación exhaustiva del soporte de Cursor en el repositorio:
1. **Existencia de Adaptador:** No existe ningún archivo `cursor-adapter.ts` en `src/adapters/` ni en ningún subpath del proyecto.
2. **Configuración y Documentación:** Existe la plantilla `docs/examples/mcp-clients/cursor_mcp.json` y las instrucciones en `docs/examples/mcp-clients/README.md` para configurar el servidor MCP de Evocara en `.cursor/mcp.json`.
3. **Dependencia de Protocolo:** La integración se basa exclusivamente en la especificación del protocolo estándar MCP JSON-RPC 2.0 sobre transporte STDIO.
4. **Pruebas y Ejecución Real:** No existen pruebas automatizadas dedicadas a Cursor en `tests/`. Históricamente fue validado en arnés protocolar genérico (`PASS_PROTOCOL_HARNESS` en R8) debido a que el binario de Cursor no reside en el PATH del entorno de pruebas.
5. **Cobertura Contractual:** El servidor estándar de Evocara (`evocara mcp --profile curated`) responde adecuadamente a las llamadas de descubrimiento y ejecución que Cursor realiza.

**Clasificación Oficial:** **`MCP_COMPATIBLE_NOT_CERTIFIED`**
- **Justificación:** Evocara no ofrece un adaptador especializado para Cursor, pero su servidor MCP implementa la especificación estándar JSON-RPC 2.0 que Cursor consume. No se afirma certificación en vivo para evitar declaraciones de compatibilidad no comprobadas empíricamente.

# CONTRATOS PÚBLICOS Y ESPECIFICACIÓN DE ESTABILIDAD v1.0.0 LTS
## Evocara Framework — Congelación Normativa de Interfaces y Garantías de Integración

---

### 1. Identidad y Propósito de Evocara v1.0.0 LTS

**Evocara** es una capa de memoria persistente, local-first, estructurada, bitemporal, selectiva, segura y auditable para agentes de desarrollo e inteligencia artificial.

- **Paquete:** `evocara`
- **Versión Normativa:** `1.0.0`
- **Licencia:** MIT
- **Entorno de Ejecución:** Node.js `>= 18.0.0` (Probado en LTS v20 y v24 en Win32, Linux y macOS).
- **Tipado:** TypeScript `5.x` con definiciones canónicas completas (`.d.ts`).
- **Principios Inviolables:**
  1. *Local-First:* Cero dependencias obligatorias de servicios cloud o APIs comerciales.
  2. *Fuente Única de Verdad (SSOT):* `.openmemory/project-state.json`.
  3. *Persistencia Fiable:* Escritura atómica con `fsync` y reintentos ante bloqueos (`EBUSY`/`EPERM`).
  4. *Independencia de Consumidores:* Adaptadores desacoplados sin subordinación al núcleo.
  5. *Búsqueda Determinista:* Motor léxico OSS `MiniSearch` integrado en memoria con soporte de acentos y tolerancia tipográfica.

### 4. Contratos de Persistencia y Almacenamiento

Evocara garantiza dos motores de almacenamiento local sin intermediación remota:

#### A. Persistencia JSON Predeterminada (Canónica)
- **Ubicación:** Directorio `.openmemory/` en la raíz del proyecto.
- **Fuente Única de Verdad (SSOT):** `.openmemory/project-state.json`.
- **Garantía de Escritura Atómica:** Implementada mediante `robustAtomicWriteFileSync` (`PersistenceEngine`):
  - Escritura previa en archivo temporal (`.tmp`).
  - Sincronización a disco con `fsyncSync`.
  - Reemplazo atómico con bucle de 25 reintentos y esperas de 15 ms para tolerar bloqueos de indexadores en Windows (`EBUSY`/`EPERM`).
  - Limpieza garantizada de huérfanos `.tmp`.
- **Búsqueda Léxica Integrada:** Motor `MiniSearch` universal en memoria hidratado desde el estado JSON persistente.

#### B. Persistencia SQLite Local (Optativa)
- **Activación:** Mediante variable de entorno `OPENMEMORY_STORAGE_BACKEND=sqlite`.
- **Motor:** Módulo nativo `node:sqlite` sin dependencias externas compiladas.
- **Modo:** WAL (Write-Ahead Logging) transaccional con paridad de esquema 1:1 frente a JSON.

#### C. Aislamiento Multi-Proyecto Estricto (GAP-ISO-01)
- Cada servidor MCP y cada instancia de `StorageEngine` se confina estrictamente al directorio del proyecto instanciado.
- La validación dinámica `validateDomainId` y el confinamiento de rutas `resolveSecurePath` rechazan cualquier intento de Path Traversal (`../`) o consultas cruzadas no autorizadas con denegación fail-closed (`403 Forbidden`).

### 6. Política de Versionado SemVer y Estabilidad de v1.0.0

Evocara sigue estrictamente [Semantic Versioning 2.0.0](https://semver.org/):

1. **Garantía dentro de v1.x (Parches y Menores):**
   - No se alterarán los nombres públicos ni los esquemas de entrada/salida de las 8 herramientas curadas.
   - No se eliminará ningún subpath export declarado en `package.json`.
   - La estructura de `.openmemory/project-state.json` mantendrá compatibilidad hacia atrás mediante migraciones idempotentes de esquema.
   - Las mejoras en la fachada `StorageEngine` preservarán los métodos públicos existentes mediante delegación.
2. **Política de Deprecación:**
   - Cualquier método o herramienta que deba sustituirse será marcado con anotación `@deprecated` en TypeScript y registrará advertencias en logs de diagnóstico durante al menos un ciclo menor antes de su retiro.
3. **Cambios Reservados para v2.0.0 (Breaking Changes):**
   - El retiro físico de métodos de conveniencia de `StorageEngine`.
   - El cambio del nombre por defecto de los prefijos de herramientas MCP.
   - La alteración de esquemas de datos incompatibles sin migrador automático.
