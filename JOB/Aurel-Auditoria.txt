# Auditoría técnica integral — Ruta Sistemas

**Fecha:** 2026-11-12  
**Alcance:** estado del árbol de trabajo actual, incluidos cambios sin commit y archivos no rastreados.  
**Método:** lectura de código, documentación e historial Git; ejecución local; pruebas automatizadas; inspección del DOM accesible en navegador. No se modificó el repositorio.

## 1. Resumen ejecutivo

Ruta Sistemas no es hoy un portal de empleo operativo: es un catálogo estático, curado y explícitamente conservador. Esa decisión es técnicamente coherente con la evidencia disponible y evita publicar vacantes no verificadas. El objetivo real implementado es ayudar a comparar condiciones y evidencia de oportunidades para Sistemas en Perú, no captar postulaciones ni automatizar scraping.

**Dictamen:** la dirección del producto es correcta para un piloto de calidad de datos, pero el alcance funcional está por debajo de la visión implícita de “catálogo de oportunidades” porque no existe ninguna oportunidad real activa. La arquitectura está sobredimensionada en algunas superficies visuales para el valor actual y subintegrada en el servidor local.

Hallazgos principales:

1. **P0 — regresión verificable:** `index.html` carga `canvas.js`, pero `server.py` no lo incluye en `PUBLIC_FILES`. En la ejecución local `/canvas.js` devuelve 404 con cuerpo JSON; el navegador registra 404 y rechazo por MIME. El artefacto de Pages sí lo incluye y valida.  
2. **P1 — cambio UI sin commit:** el árbol contiene un rediseño muy grande (1.536 líneas netas en cambios rastreados) y `canvas.js` no rastreado. No debe tratarse como una versión aprobada hasta consolidar, revisar y probar el conjunto.  
3. **P1 — valor de producto:** el catálogo contiene cinco registros demostrativos, todos no publicables; no hay una ruta operativa de incorporación editorial, solo transferencia manual a la semilla.  
4. **P1 — coherencia de marca:** la UI visible usa `Aurel`/`AurelDev`, mientras README, footer y producto usan Ruta Sistemas. Esto afecta identidad, SEO, confianza y trazabilidad del piloto.  
5. **P2 — cobertura:** las pruebas verifican contratos estáticos y lógica extraída con `vm`, pero no cubren la ejecución completa del servidor local, carga de `canvas.js`, accesibilidad real, responsive ni interacción completa de modales/comparador.

Las 56 pruebas Python y las validaciones de catálogo/JavaScript pasan. Esto demuestra consistencia de contratos, no que el flujo publicado esté íntegramente operativo.

## 3. Auditoría de cambios recientes UI/UX

### Cambios observados

### Problemas funcionales y visuales

- **Canvas roto en local:** `index.html:1054` carga `canvas.js`; `server.py:279-286` no lo publica. Esto contradice el flujo documentado `python server.py`.
- **Marca inconsistente:** `index.html:11` dice `<title>Aurel</title>` y el DOM muestra `AurelDev`, mientras el footer dice `rutasistemas` y README identifica Ruta Sistemas.
- **Complejidad visual no proporcional al catálogo:** el hero WebGL y la animación agregan superficie de rendimiento, compatibilidad y accesibilidad sin resolver la ausencia de datos activos.
- **Reduced motion parcial:** hay una regla `prefers-reduced-motion`, pero el canvas sigue siendo una animación WebGL propia; no hay evidencia de que el bucle de renderizado se detenga o reduzca su coste, solo de que CSS reduzca animaciones.
- **Comparador no probado end-to-end:** la lógica está cubierta parcialmente por pruebas sintéticas, pero no hay prueba de abrir dos fichas, mostrar el diálogo y cerrarlo en navegador.
- **Carga de errores demasiado genérica:** `app.js:586` usa `catch {}` y descarta la causa técnica. La UI sí muestra estado de error, pero la ausencia de diagnóstico dificulta operar el piloto.
- **Dependencia de estado artificial:** la UI funciona con fichas demostrativas solo después de una acción explícita. Esto es correcto editorialmente, pero deja la primera visita sin contenido accionable y debe medirse con usuarios antes de seguir ampliando la presentación.

### Qué conservar

- Separación entre `opportunityStatus`, `verificationStatus` y `publicationStatus`.
- Opt-in explícito para demostraciones, no confirmadas e históricas.
- Detalle que diferencia empleador, publisher, fuente y canal de postulación.
- Comparación sin score ni conversión de ausencia a “malo”.
- CSS compilado localmente, sin CDN runtime.
- Estados de carga/error y navegación con teclado en la lógica existente.

### Qué corregir o revertir

1. Corregir inmediatamente el contrato de `canvas.js` local o eliminar el canvas hasta que tenga valor validado.
2. Unificar `Ruta Sistemas` como marca, título, metadata y texto accesible.
3. No ampliar más la hero visual antes de validar comprensión y tarea principal con usuarios.
4. Añadir pruebas de navegador para carga local, canvas, detalle y comparador.

## 4. Arquitectura actual identificada

### Capas reales

1. **Presentación:** `index.html`, `app.js`, `styles.css`, `src/input.css`, `src/site.css`, `canvas.js`.
2. **Contrato de datos:** `data/opportunities.seed.json` → `scripts/build_catalog.py` → `data/opportunities.json`.
3. **Validación:** `scripts/catalog_quality.py`, `validate_catalog.py`, `validate_candidates.py`, pruebas Python y Node.
4. **Fuentes/conectores:** `collector/policy.py`, `collector/ats_connectors.py`, `collector/refresh_catalog.py`, `collector/sources.json`.
5. **Prototipo local:** `server.py` + SQLite local, no conectado al frontend público.
6. **Publicación:** GitHub Actions compila CSS, valida y prepara cinco archivos para Pages.

### Flujo real

`seed.json` → validación/generación → `opportunities.json` → carga relativa desde `app.js` → filtrado en memoria → detalle/comparación local → publicación Pages.

El servidor Python expone una API SQLite local (`/api/opportunities`) y archivos estáticos limitados, pero la UI no consume esa API. Hay dos caminos de lectura que no comparten una fuente runtime:

- Pages: JSON estático.
- Local: SQLite inicializado desde la semilla al arrancar.

La separación está documentada y es aceptable para un prototipo, pero duplica lógica y puede inducir falsas expectativas sobre qué se está probando.

## 5. Flujo de trabajo real de extremo a extremo

1. Una persona edita `data/opportunities.seed.json`.
2. `build_catalog.py` genera o comprueba el snapshot.
3. Los validadores comprueban esquema, fechas, estados, hosts y consistencia.
4. CI ejecuta pruebas, compila CSS, valida y prepara el artefacto exacto.
5. Pages publica `index.html`, `app.js`, `canvas.js`, `styles.css` y el JSON.
6. El navegador carga el JSON y filtra en memoria; no hay sesión, cuenta, postulación ni persistencia.
7. El colector no consulta fuentes: si una fuente está habilitada, falla cerrado hasta una migración/revisión explícita.

El flujo es seguro para no publicar datos no autorizados, pero no es un flujo de mercado vivo. El primer cuello de botella no es técnico: es autorización, fuente y proceso editorial.

## 7. Fortalezas arquitectónicas

- Contrato de datos explícito y versionado.
- Semántica de estados mejor que un único `status`.
- Política fail-closed para automatización y redirecciones.
- Hosts HTTPS allowlisted y evidencia temporal.
- No confunde `generatedAt` con verificación de una vacante.
- Permisos CI mínimos (`contents: read` en validación).
- Artefacto Pages cerrado y comprobado byte a byte.
- Tests centrados en invariantes importantes: demostraciones, fechas, rutas Pages, evidencia y degradación ante catálogo inválido.
- Documentación honesta: declara límites, no inventa usuarios ni resultados.

No encontré evidencia para afirmar vulnerabilidades explotables en el alcance revisado. Sí existe riesgo potencial de incompatibilidad WebGL y coste de renderizado en equipos modestos; requiere medición, no debe presentarse como defecto medido.

## 9. Componentes que deberían simplificarse

1. **Hero WebGL:** eliminar o convertir en mejora opcional hasta validar impacto en comprensión, rendimiento y accesibilidad.
2. **Evaluación por ficha:** conservar las señales, pero evitar repetir contenido editorial en demasiadas capas si el catálogo sigue vacío.
3. **Servidor SQLite:** mantenerlo solo como fixture local claramente separado; no seguir ampliándolo sin requisito de curación concurrente.
4. **Conectores ATS:** conservar las políticas y adaptadores como investigación, pero no añadir más conectores antes de resolver autorización y schema 2.
5. **Documentación histórica en el árbol principal:** separar decisiones vigentes de snapshots para reducir ambigüedad.

## 10. Candidatos a sustitución OSS

No recomiendo sustituir la aplicación estática por un framework ni añadir un backend ahora. Los candidatos dependen de la decisión de producto pendiente:

- **Curación Git-based:** Decap CMS podría reemplazar la copia manual a la semilla cuando exista un flujo editorial estable. Su repositorio oficial es [decaporg/decap-cms](https://github.com/decaporg/decap-cms), licencia MIT, 19.5k stars y 4.8k commits observables al momento de la auditoría. Ventaja: conserva Git y encaja con Pages; desventaja: auth/deploy y validaciones de dominio siguen requiriendo diseño. Adoptar solo después de definir roles, revisión y promoción.
- **Servidor autoalojado futuro:** Caddy podría sustituir el servidor alojado cuando exista capacidad operativa. [caddyserver/caddy](https://github.com/caddyserver/caddy) usa Apache-2.0 y ofrece HTTPS automático. Ventaja: despliegue simple; desventaja: no resuelve datos, curación, backups ni observabilidad. No integra ahora.
- **Backend/CMS headless:** Directus es técnicamente capaz, pero sería sobreingeniería para cinco fichas y añade una plataforma de datos, auth y operación. No se recomienda en esta fase; se debe comparar formalmente licencia/edición, coste operativo y necesidad de multiusuario antes de adoptarlo.

Ya se usa Tailwind CSS CLI fijado y compilado localmente. No hay motivo para introducir otro sistema de componentes. GitHub Pages/Actions no son OSS, pero la documentación los identifica correctamente como servicios hospedados y mantiene una salida portable.

## 13. Riesgos por horizonte

### Corto plazo

- publicar una UI con marca incorrecta;
- que el desarrollo local no reproduzca Pages por `canvas.js`;
- introducir regresiones visuales no cubiertas por tests;
- mantener la percepción de “catálogo” sin oportunidades utilizables.

### Medio plazo

- divergencia entre SQLite local y JSON canónico;
- proceso editorial manual lento o inconsistente;
- más features de evaluación sobre datos insuficientes;
- dependencia de Pages/Actions sin procedimiento operativo alternativo probado.

### Largo plazo

- necesidad de auth, roles, historial y auditoría si el catálogo crece;
- obligaciones de licencia/atribución/retirada de fuentes;
- coste real de hosting, backups, monitorización y disponibilidad;
- migración compleja si se convierte el prototipo en backend sin fijar contratos.

## 15. Recomendación final como Principal Engineer

No reescribiría el proyecto. Mantendría el modelo estático, el contrato de evidencia y el enfoque fail-closed. Detendría temporalmente la expansión visual y cerraría primero la integridad del entorno local, la marca y el primer flujo editorial con una fuente autorizada.

La prioridad no es añadir IA, ranking, scraping general, Directus ni un backend multiusuario. La prioridad es demostrar que una persona puede encontrar una oportunidad real, entender sus límites y comprobar el canal de postulación con evidencia reciente. Si ese flujo no logra valor con una fuente autorizada, más arquitectura no arreglará el producto.

## Dictamen final directo

- **¿Cumple el objetivo original?** Cumple el objetivo reducido de catálogo explicable y curado; no cumple todavía un objetivo de oportunidades activas.
- **¿La arquitectura es adecuada?** Sí para un piloto estático; no para curación concurrente o operación de mercado sin una decisión explícita de backend.
- **¿Los últimos cambios UI son mejora real?** Mejoran jerarquía, detalle y comparación, pero su valor está limitado por la ausencia de datos reales y tienen una regresión local verificable.
- **¿Qué conservar?** Estados separados, evidencia, opt-in de demos, filtros, comparación sin score, validación fail-closed y artefacto Pages.
- **¿Qué corregir/revertir?** Integración de `canvas.js`, marca `Aurel`, falta de E2E y cualquier animación que no aporte a la tarea principal.
- **¿Qué está sobredimensionado?** Hero WebGL y expansión de evaluación visual antes del primer piloto real.
- **¿Dónde se pierde tiempo?** En polish visual y documentación/código alrededor de fuentes no autorizadas, mientras la incorporación editorial real permanece manual.
- **¿Qué OSS puede acelerar?** Decap CMS para edición Git cuando el proceso esté definido; Caddy solo para una futura salida autoalojada.
- **¿Principal problema a resolver primero?** Cerrar el flujo de datos real y verificable, después de corregir el fallo local de `canvas.js`.
- **¿Qué haría para producción?** Congelaría el alcance, arreglaría los contratos de ejecución, unificaría marca, validaría con usuarios y ejecutaría un piloto pequeño de una fuente autorizada antes de seleccionar CMS, backend o infraestructura nueva.
